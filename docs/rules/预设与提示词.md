# 预设与提示词

参考「静态打底、动态补此刻」的拼装思路，结合岛屿机自己的玩法重新设计。

## 一、总原则

一条请求按 **A → B → C** 拼装，最后再接聊天记录和本轮输入：

- **A 静态基础**：变化很少，可以命中缓存，只算一次
- **B 每轮动态**：每一轮重新算，取不到的块直接跳过
- **C 任务预设**：每个 App 自己的玩法和回复格式，永远在最后

为什么 C 放最后：先把角色、记忆、环境都说清楚，最后再说输出格式；换 App 只需要换这一段。

最终请求 = A + B + C → 上下文深度/聊天记录 → 本轮输入。

## 二、完整结构（从上到下）

### A 静态基础（命中缓存）

| 序号 | 块 | 内容 |
|---|---|---|
| A1 | 世界书·最高 | 最高优先级设定（破限），整条提示词最前 |
| A2 | 系统核心 SYSTEM_CORE | 岛屿机底层规则：真人感、不 OOC、没有 AI 味、不限制长度（见《角色与人生.md》） |
| A3 | 语言与文风规则 | 回复语言、标点习惯、文风、是否分多条消息 |
| A4 | 世界书·前 | 放在角色资料之前的世界书 |
| A5 | 当前角色资料 | 人设、口吻、关系、屿年里当前阶段摘要 |
| A6 | 用户资料 | 当前启用的 user 人设 |

缓存键：角色 + 人设 + 用户 + 世界书（最高/前）+ 语言规则 + 预设版本。任何一项变化就重算。

### B 每轮动态（每轮重算，取不到就跳过）

| 序号 | 块 | 内容 |
|---|---|---|
| B1 | 记忆 | 总结记忆 + 向量检索到的相关记忆（按用户设置的深度） |
| B2 | 世界书·中 | 紧接在角色资料和记忆之后 |
| B3 | 角色当前状态 | 日历里此刻在做什么、今天的心情、在不在线 |
| B4 | 时间与上次对话 | 现在几点、星期几、距离上次聊天多久；空白期超过 6 小时才加「这段时间角色在做什么」 |
| B5 | 内在驱动 | 驱动状态、稳定念头（默认只读观察，开启后才注入，见《内在驱动系统.md》） |
| B6 | 联动区块 | 最近朋友圈、论坛、相册、相遇、情侣空间、美团等 App 的近况（按互通表，只给相关的） |
| B7 | 计划与提醒 | 聊天里的约定、纪念日、待办 |
| B8 | 世界书·后 | 放在上下文深度/聊天记录、本轮输入之前 |

取舍规则：
- 任何块取不到内容，直接跳过，不补空标题
- 每个块用「=== 标题 ===」包起来，让模型分得清
- 联动区块只放和当前对话相关的，不置顶堆满
- 栖迟的「番外小剧场」内容永远不进这里

### 接在 B 之后（不属于系统提示词本身）

- 上下文深度/聊天记录：最近 N 条原文，N 由用户自定
- 本轮输入：user 这一句话

### C 任务预设（永远在最后）

每个 App 一份，只写：玩法、场景、任务、回复格式。

| App | 补什么 |
|---|---|
| 聊天 | 使用手机聊天的语气；回复格式（文字、转账、图片、表情包、语音等消息类型的输出结构）；是否拆成多条 |
| 群聊 | 多角色轮流发言的格式 |
| 相遇 | 长篇叙事、旁白动描、文风、是否计入记忆 |
| 日历 | 生成当天日程的格式 |
| 屿年 | 年度成长记录的格式 |
| 论坛 | 发帖、评论、NPC 轮流发言 |
| 文学城 | 小说生成规则 |
| 情侣空间 | 便利贴、日记、纪念日的格式 |
| 栖迟 | 梦境文游、选项、结局、番外的格式 |
| 美团 | 订单、送达、留言的格式 |
| 查岗 | 查手机时的反应 |
| 内在驱动·醒来 | 决策输出（JSON） |

写法：每个 C 以「=== 任务指令 ===」开头，先说任务，最后写输出格式的硬性要求。格式要求放最后，的好处是模型先理解语境再按格式输出，换 App 只换这一段。

## 三、用户可以自己调整的地方

- A、B 里的模块可以：开关、改顺序、编辑内容、删除、新增自定义模块
- 自定义模块默认放在 B 里，可选择放 A 或 B
- 固定不动：「最高」永远在最前，C 永远在最后（为了保证输出格式不被盖掉）
- 世界书的四个位置对应上表固定位置，规则见《世界书管线.md》
- 预设可以保存成多套、编辑、更新、删除、导入导出，各 API 位置可选用不同的一套

## 四、共用读取流程

角色资料（A5）、用户资料（A6）、世界书（A1/A4/B2/B8）、记忆（B1）统一由「共用读取流程」拼好，所有 App 都走它，不允许各 App 自己另写。

## 五、开发规则

1. 新 App 动手前，先写清「读什么（用哪些块）、结束后存什么」
2. 改共用部分（A、B）时，必须一起检查所有旧功能是否正常
3. 各 App 只补自己的 C，不动 A、B
4. 最终请求里的块按当前对话逐项判断是否出现
5. 不限制上下文 token，长度由所接模型自己决定
6. 拼装结果开发期可在设置里查看“本次实际发送内容”，方便排查（仅开发者可见）
