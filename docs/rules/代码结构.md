# 代码结构规则

## 一、怎么分文件

- 一个文件只管一类事。界面、存取数据、调用模型,各自独立文件。
- 参考大小:界面文件超过约 400 行、其他文件超过约 300 行,就要考虑拆。
- 一个文件里出现两个以上不相干的功能,马上拆。
- 多个 App 都用得到的(弹窗、主题、读取流程、网络、通用列表),统一放 `core/` 或 `ai/`,只维护一份。

## 二、命名

- 文件名说清它管什么:`ChatListScreen`(界面)、`ChatRepository`(存取)、`ChatPromptBuilder`(拼提示词)。
- App 文件夹用固定英文名:chat、appearance、years、album、calendar、settings、worldbook、music、meet、patrol、forum、novel、couple、preset、meituan、dream。

## 三、新增功能

- 沿用已有结构和已有共用组件,不另起炉灶。
- 先看 `core/`、`ai/` 里有没有现成的,有就用。
- 新 App 动手前写清:读取哪些信息、结束后保存什么(写进该 App 的设计说明)。

## 四、修改与整理

- 更新优化时,**不能随意删除没涉及到的代码**;涉及到的才可以改或删。
- 要动共用部分,先列出会影响的已有功能,改完逐个检查。
- 整理代码(拆文件、改名)后,必须检查原有功能是否正常,交代里说明检查了哪些。
- 删除功能代码前,先查有没有别处在用。

## 五、版本号

- 每次更新、优化默认升版本:改 `version.properties` 的 `VERSION_NAME` 和 `VERSION_CODE`(后者只增不减)。
- 升版本方便 user 刷新、覆盖安装。

## 六、网络与流式

- 流式输出自己用原生网络层实现,统一放 `ai/stream/`,各厂商格式(Claude、GPT、Gemini、DeepSeek、GLM 等)做成可替换的适配器。
- 每个 API 槽位(聊天、记忆总结、向量、重排、识图、语音、转文字、生图)可单独选流式或非流式。
- 请求要有超时、重试、取消。

## 七、保活

- AI 请求在前台服务里跑,不绑定在页面上。
- 页面只订阅结果;页面销毁不影响请求。
- 通知栏显示进行中状态,完成时可发系统通知(受设置开关控制)。

## 八、预留

- 快捷键:预留统一入口。
- 本地模型:预留模型调用接口,让本地模型能像在线模型一样接入。
- 缓存:预留分层缓存接口。

## 九、交付前自检

- [ ] 没删没涉及的代码
- [ ] 日夜间/跟随系统/手动 都正常
- [ ] 左右滑返回正常
- [ ] 新增内容有编辑和删除,新增功能有关闭
- [ ] 弹窗用专属样式
- [ ] 没加小字注释
- [ ] 版本号已升
- [ ] 回复里写了:改了什么、哪些文件、几个文件
